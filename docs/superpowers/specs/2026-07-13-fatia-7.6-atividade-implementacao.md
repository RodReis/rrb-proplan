## Decisões de arquitetura (fixadas com o PI, 2026-07-13)

1. **Módulo novo `activity`** — dono do modelo `Operation` e da composição do histórico. `board` e `insight` injetam `ActivityService` pela interface pública (nunca importam entidade interna — CLAUDE.md). Precedente: `SharedModule`/`GithubWritebackClient` já resolve compartilhamento board↔insight, mas `Operation` tem entidade + service + controller + polling — perfil de módulo, não de client sem estado.
2. **Fix mínimo do promote foi revertido** — implementação parte da spec, sem paliativo costurado.
3. **Estado no servidor** — `Operation` é a fonte; o front só faz polling. F5 no meio retoma (critério de aceite).

## Modelo de passos (o coração da Camada 1)

Cada fluxo de escrita é `ação → commit → propagação → sync → recarregar`. Modelo genérico de passos, com **texto por fluxo**:

```
Operation {
  id, projectId, kind: 'promote'|'bootstrap'|'board_mutation'|'mapping',
  status: 'running'|'done'|'failed',
  steps: Step[],           // Json
  commitUrl?, syncRunId?,  // artefatos
  error?, startedAt, finishedAt?
}
Step { key, label, status: 'pending'|'running'|'done'|'failed' }
```

Passos por `kind` (texto em linguagem de gente, **nunca** jargão):

| kind | passos |
|---|---|
| `promote` | `Commitando docs/ARCHITECTURE.md no repositório…` → `Aguardando o GitHub propagar o commit…` → `Sincronizando a documentação…` → `Pronto — a aba agora usa o documento real` |
| `mapping` | `Salvando o mapeamento no repositório…` → `Aguardando o GitHub propagar…` → `Sincronizando…` → `Pronto` |
| `bootstrap` | `Commitando docs/STATUS.md no repositório…` → `Aguardando propagar…` → `Sincronizando…` → `Pronto` |
| `board_mutation` | `Atualizando a issue no GitHub…` → `Confirmando a mudança…` → `Pronto` |

O passo "Aguardando propagar" existe hoje (a espera é real — SHA-aware). Quando o `sleep` sair de vez, o texto continua válido (a espera vira verificação, mas ainda é espera).

- Back: `GET /projects/:id/activity?cursor=` — **projeção de leitura** que une `Operation` (em curso) + `SyncRun`+`Insight`+`BoardMutation` (histórico), ordem reversa, paginada. `LlmUsage` entra quando a 7.5 existir (degradação graciosa: ausente = sem custo). **Não** cria tabela de eventos.

- Front: `<ActivityPanel/>` no rail (`Home.tsx`), abrível de qualquer tela, **por projeto**. Seções "Agora" (operações em curso, sobrevive à navegação — vive no shell, não na aba) + "Histórico" (link do commit clicável → GitHub).

## Riscos / pontos de atenção

- **"Sobrevive à navegação"** exige que a operação em curso viva no **shell** (Home/Workspace pai), não na aba que a disparou. O `operationId` sobe pro pai; a aba só o inicia. Decisão de onde o estado de "operações ativas" mora no React: no `Workspace` (por projeto), passado ao `ActivityPanel`.
- **Polling múltiplo**: várias operações ativas = vários pollings. Cap simples (uma operação de escrita por vez por projeto é o caso real) — não otimizar antes de medir.
- **Histórico como projeção**: unir 4 tabelas com ordenação/paginação por data. Cursor por timestamp. Sem índice novo além dos que já existem (`@@index [projectId, createdAt/startedAt]`).
- **Degradação**: `LlmUsage` não existe até a 7.5. O histórico deve funcionar sem ela (try/catch ou feature-flag por existência da tabela).

## O que NÃO fazer (fora de escopo, da spec)

Log técnico/stack trace, SSE/websocket, notificação fora da aba, cancelar operação, filtro/busca no histórico, retenção configurável.
