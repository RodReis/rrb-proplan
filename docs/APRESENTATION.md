**ProPlan**

Transparência e governança nos projetos que desenvolvo para você — visibilidade real, sem depender de reunião de status.


# **O problema que toda empresa que contrata software conhece**

Quem paga pelo desenvolvimento de um sistema quase nunca consegue enxergar, com os próprios olhos, em que pé ele está. A resposta depende de perguntar à equipe — e a resposta da equipe nem sempre bate com a realidade. Três situações se repetem em praticamente todo projeto:

- **O “está quase pronto” eterno. **O status vive na cabeça de quem desenvolve, e cada pergunta gera uma resposta diferente.

- **A entrega que ninguém validou. **O desenvolvedor declara “terminei”, o assunto morre — e semanas depois descobre-se que faltava metade.

- **O projeto que ficou órfão. **A pessoa que sabia tudo saiu, o projeto parou, e retomar custa quase o preço de refazer.

# **Como eu trabalho: o ProPlan**

O ProPlan é o painel de gestão que desenvolvi e uso para conduzir todos os projetos em que atuo. Ele se conecta ao repositório do projeto no GitHub (onde o código e a documentação vivem) e monta um workspace visual que responde três perguntas: o que é este projeto, onde ele parou e o que falta. Contratando meus serviços, você acompanha o seu projeto por esse painel — em linguagem de negócio, não de programador.

Um ponto importante de segurança: o painel lê apenas a documentação do projeto — nunca o código-fonte. Ele não copia nem armazena o seu sistema; a fonte de verdade continua sendo o repositório do projeto, que é seu.

# **As visões do workspace — o que cada uma responde**

Cada projeto conectado ganha um workspace com abas. Cada aba responde uma pergunta de gestão específica:

| **Visão** | **O que ela entrega para a gestão do projeto** |
| - | - |
| **Visão Geral** | O resumo executivo do projeto: o que ele é, onde parou e o que falta — atualizado a partir do repositório. É a primeira tela para responder “como estamos?” sem reunião. |
| **Documentos** | Toda a documentação do projeto reunida e navegável em um só lugar, com indicação do que existe, do que está desatualizado e do que ainda não foi documentado. |
| **Kanban** | O quadro de tarefas oficial do projeto: backlog, a fazer, em andamento, feito e finalizado. Separa o que foi entregue do que foi aceito — a validação final é sempre sua. |
| **Grafo** | Um mapa visual de como os documentos se conecta entre si. Mostra o encadeamento das informações e revela documentos isolados ou esquecidos. |
| **Decisões** | O histórico das decisões importantes do projeto com o porquê de cada uma. Evita rediscutir o que já foi decidido e explica escolhas para quem chega depois. |
| **Arquitetura** | Como o sistema é desenhado por dentro, em uma visão organizada — útil para avaliar impacto de mudanças e para integrar novos fornecedores ou desenvolvedores. |
| **Skills & Agentes** | Quais ferramentas e assistentes de IA o projeto utiliza no desenvolvimento — transparência sobre o que é feito por humanos e o que é apoiado por máquina. |
| **Testes** | O projeto foi testado? Como e com que frequência? Mostra a estratégia de qualidade e os ciclos automáticos de verificação. |
| **Design** | Os padrões visuais e de interface do produto: identidade, componentes e regras de usabilidade que garantem consistência nas telas. |
| **Deploy** | O sistema está em produção? Em quais plataformas roda? Responde onde o produto vive de verdade — e alerta quando há sistema no ar sem documentação disso. |
| **Contexto** | O que só existia na cabeça de quem desenvolve — “por que paramos”, “no que não mexer” — registrado com autor e data. É o seguro contra a saída de pessoas-chave. |
| **Handoff** | Um instantâneo completo e exportável do estado do projeto, pronto para entregar a um novo fornecedor, sócio ou equipe — a transição sem refém. |


# **Onde ele tira a sua dor**

| **A dor de hoje** | **Como o ProPlan resolve** |
| - | - |
| “Como está o projeto?” só se responde perguntando ao desenvolvedor. | A aba Visão Geral responde em uma tela: o que é o projeto, onde parou e o que falta — em linguagem de negócio, sem precisar abrir código nem agendar reunião. |
| “Terminei” que não terminou: a entrega é declarada, mas ninguém validou. | O quadro de tarefas separa “Feito” (entregue, aguardando validação) de “Finalizado” (aceito pelo dono). Só quem manda no projeto dá o aceite — nenhuma automação ou desenvolvedor consegue forçá-lo. O histórico de quem aceitou o quê, e quando, fica registrado. |
| A documentação mente: o papel diz uma coisa, o sistema em produção é outra. | O ProPlan compara a documentação com sinais reais do projeto e alerta quando elas se contradizem — por exemplo, documentação parada há meses enquanto o código continua mudando, ou um sistema no ar sem nenhuma página explicando onde e como ele roda. |
| Projeto parado que ninguém consegue retomar sem depender de quem o fez. | O painel reconstrói o contexto a partir do que está escrito no repositório e registra o que só existia na cabeça de alguém (“por que paramos”, “no que não mexer”) com autor e data. Retomar deixa de depender da memória de uma pessoa. |
| Vários projetos, nenhuma visão do conjunto. | Um catálogo único lista todos os projetos com seu estado — o que está em produção, o que está parado, o que tem pendência de validação — e sinaliza risco antes de virar problema. |


# **Três princípios que sustentam a confiança**

- **O aceite é sempre humano. **Nada é dado como concluído porque um sistema disse que sim. A palavra final é sempre do dono do projeto — e o ProPlan foi desenhado para que isso não possa ser burlado.

- **Inteligência artificial identificada e revisável. **Quando um resumo é gerado por IA, ele vem sinalizado como tal e pode ser revisado. O que o humano escreveu tem sempre prioridade sobre o que a máquina inferiu.

- **Seus dados continuam seus. **Todo o estado do trabalho vive no seu GitHub, em formato aberto. Se um dia deixar de usar o ProPlan, nada se perde — não há aprisionamento.

# **O que isso significa para o seu negócio**

- **Transparência contínua: **acompanhe o andamento a qualquer momento, sem esperar a próxima reunião de status.

- **Entregas com validação formal: **cada entrega passa pelo seu aceite — o “terminei” sem validação deixa de existir.

- **Menos dependência de pessoas: **o conhecimento do projeto fica registrado e organizado, não na memória de um desenvolvedor.

- **Alerta antes do prejuízo: **documentação defasada e projetos à deriva são sinalizados cedo, quando ainda é barato corrigir.
